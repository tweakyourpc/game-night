# Identity and access

We recommend a separate Google account to keep Game Night mail, Drive files, and service authorizations separate from personal or everyday work activity. **This is optional.** The Google account that deploys with **Execute as: Me** authorizes Sheets, Drive, URL fetch and mail operations. It sends invitations and reminders through MailApp and owns the installation's `Game Night files` Drive folder; the game spreadsheet contains the game data. Players use the web-app link and do not need access to that spreadsheet.

Use the same account for setup, deployment, optional repair triggers, and manual repairs. Triggers execute as their creator, while manual repair executes as the person invoking it; both can send queued mail and access Drive. Google Workspace administrators may restrict public web apps or authorization. Personal and organization-managed Google accounts are supported where policy permits. Google mail delegation, aliases, and shared mailboxes are outside the kit and must be configured separately if desired; they do not change which account this deployment executes as. The kit does not require Workspace or a Google Cloud service account.

**A dedicated deployment account does not strengthen player authentication.** The shared code, trusted/PIN modes, and device sessions described below stay the same. The script still has its requested permissions on the account running it, and the spreadsheet owner and editors can read or change its data and code. Keeping other data out of that account separates activity without creating a security sandbox.

A visitor's Google identity is not used to establish game identity. Anonymous web access allows the entry page to load; it does not bypass the group code or application session checks.

The shared code is a group admission secret, stored as plaintext in Settings and visible to signed-in members for invitations. Matching ignores case and repeated whitespace. Anyone who learns it can list active names and create a member. In **trusted** mode they can also choose any ordinary member's name, act as that member, and see that member's private rack. This is intended for a mutually trusted group. Admin identities always require their PIN. In **PIN** mode existing members require their 4-8 digit PIN; new people choose a PIN when creating their name. PIN mode does not verify real-world identity or stop new-account registration by code holders.

Each sign-in issues a random device token stored in browser localStorage; only its SHA-256 hash is saved in Sessions. PINs use salted SHA-256, not a slow password KDF. Five failed PIN attempts cause a best-effort ten-minute cache lockout; cache eviction can clear it. This is not strong authentication for an exposed public service. Session tokens have no time-based expiry in v0.1.0. Signing out revokes that device; admin removal revokes the member's sessions. Changing the shared code does not by itself revoke existing sessions. Removing a member does not prevent a code holder creating another identity; rotate the code too when excluding someone.

Tokens are sent in RPC arguments, never invitation URLs. Table share keys locate a table and are not authentication tokens. Invitation text optionally includes the group code (off initially). Avoid forwarding it outside the group. Ordinary authenticated members can inspect public matches and replays; invite-only tables restrict taking seats, not confidential viewing. Replays include stable member IDs, display names, table titles and public moves, but not private racks or the draw bag. Treat exported names as personal data.

Admins control group settings, member PIN reset/removal and Drive exports. Hosts control their tables; presence loss neither removes seats nor transfers hosting. The spreadsheet owner and editors can read and change all underlying data/code and are fully trusted. Hashing sessions does not protect against someone who can edit the spreadsheet or script.

A copied sheet contains readable copied rows until setup clears them. Runtime isolation prevents the copy using inherited bindings to operate the original; it is not protection from an editor intentionally modifying source or copying data. Keep Sheet sharing separate from web-app access.
